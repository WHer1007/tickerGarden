# 当前慢 SQL 检查与优化（2026-09-20）

状态：生产只读诊断完成；查询改造及索引已在本地实现，尚未发布。沿用前一任务待发布的 `0030–0033` 结构迁移；未修改已经部署的 `0001–0029`。

## 已确认的当前瓶颈

采集生产 confirmed-display / resident-worker 最近两小时日志，按已有 SQL 指纹聚合。`e99ec2af7a6c02ce` 在 `stats.publish` 中出现 12 次超过 500ms 的慢 SQL，累计约 9.13 秒、单次最长约 1.793 秒。指纹与 Stats 配置读取 SQL 精确匹配。所采日志内 61 次 stats.publish，display.prepare / display.advance 未记录其他超过阈值的 SQL；任务本身慢不等于 SQL 慢。

旧查询把 `projection_read_records` 历史联合视图与当前 publication pointer 连接。生产 EXPLAIN ANALYZE 结果：

- 返回 392 条配置，却扫描 403,368 行，连接阶段排除 402,976 行。
- 访问 62,516 个 shared buffer 块，其中 58,252 个需要读入；执行 568.693ms。
- 只增加显式 revision 条件仍是 Parallel Seq Scan，耗时 222.331ms，未解决读取整表。
- 原因是联合视图分支与 domain/text 类型转换使 deployment 条件未能下推到原表索引筛选，不能仅凭 SQL 表面存在 WHERE 就认为查询已被索引约束。
- 在生产原表上，以同样条件直接按现行 revision 精确查询，使用主键，返回相同 392 条数据，仅访问 80 个 shared buffer 块，执行 0.729ms。此实验仅 SELECT，没有修改线上应用；不是已发布后耗时承诺。

## 本次改动

1. **Stats 配置读取**：通过 publication pointer 定位 `config_publication_sets.set_id`，直接读取该集合的成员与内容。不再经过历史联合视图。配置缺省时仍使用既有 runtime 配置作为补充，不改变业务含义。
2. **配置分页 API**：按已经核验的 revision 定位 set_id，再分页读取。保留 canonical/finalized 区块核验、签名游标、kind 过滤和历史版本读取。
3. **执行计划回归保护**：在 392 条配置、1,000 个历史发布锚点下，验证只读取一个发布锚点；分页的 canonical/finalized 检查每次查询只执行一次，不随配置条数重复扫描区块。保持缺少当前 pointer 时 Stats 的 runtime fallback，以及配置 API 对不可用/非 canonical 发布的拒绝。

没有调大全局 work_mem、关闭资金校验、加快轮询，也没有改变 API 响应和前端页面。

## 不应混淆的其他 SQL

- 旧报价排序曾大量超时，但生产已经压缩到 196 条当前报价；前一检查实测内存排序约 1.3ms，当前不是同等级瓶颈。
- 生产只有 2 条 market_trades、17 条 chain_logs。Stats 初始化和详情历史补齐中虽有排序，但当前数量不足以解释大量耗时；详情补齐还受 hydrated 标志限制。没有为这些未证实热点额外增加重型索引或重写业务链路。
- 累计 seq_scan/seq_tup_read 不等于当前慢 SQL 排行。一行表的顺序扫描往往合理；本次针对已关联任务日志和真实计划的历史全表扫描改造。

## 验证与发布条件

本地 PostgreSQL 功能回归覆盖配置历史读、重组/最终确认校验、Stats、详情与统一排名；增加大量发布锚点共享配置集合时的执行计划回归。最终配置计划：Stats 配置查询主体约 0.131ms、32 shared buffer 块；末页读取主体约 0.120ms、34 块。锚点和区块均通过主键读取一行、一次执行，没有历史投影扫描或临时写入。这是本地合成样本，不能作为生产延迟承诺。

本次还试验了 rank 顺序索引。单独的排名游标 SQL 在 5 万行下确实变快，但真实 Explore 联合卡片查询在新数据尚未 ANALYZE 时被错误估算为极少行，导致排序索引前缀或连接内层被反复扫描，2 万项目触发 5 秒超时。该索引方案未纳入最终代码，原排名 SQL 和索引方案保持不变；恢复后实际 Explore 市值排序测试约 80ms、其他排序 24–31ms、50 张卡片读取约 7ms，20,003 个卡片全部通过。保留这个实验结论以避免以后仅凭独立索引小样本就上线。

发布时先按既有维护窗口执行 `0030–0033` 和权限更新，再切换 Read API / Pipeline / Worker。查询依赖新配置集合表，不可跳过迁移直接发布。上线后以新的 SQL 指纹和统计任务耗时验证收益。

观察范围限制：生产尚无 pg_stat_statements，此次覆盖已有 Worker 日志和针对性生产 EXPLAIN，不能声称捕获了所有 Vercel 实例的全部 SQL 或建立完整全库慢查询排行榜。建议后续在计划维护窗口补齐数据库级 SQL 聚合监控。
