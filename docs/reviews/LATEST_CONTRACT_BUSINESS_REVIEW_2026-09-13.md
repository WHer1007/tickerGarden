## 需要处理的实现问题

### LBR-01｜中：外部资产余额可使 Locker 复投反复回滚

位置：`contracts/src/v1/shared/LaunchLockerCompounding.sol:90`、`:99`、`:108`；vendored `contracts/lib/v4-periphery/src/PositionManager.sol:499`。

复投调用在 PositionManager 中执行两次 `SWEEP`，该操作扫出的是对应资产的**全部合约余额**，不只本次操作的退款。因此任何人预先转入 PositionManager 的同种资产，也会回到 Locker。若外来余额超过该次投入，使 Locker 的结束余额高于开始余额，`CompoundBalanceMismatch` 会使复投整体回滚；外来余额也留在 PositionManager，下次重试仍可失败。

本轮重跑现有真实 PoolManager/PositionManager 测试：ERC20 和 native 两种情况均复现；测试先注入 100 单位外来资产、尝试最多投入 60，清走 PositionManager 外来余额后复投恢复。Permit2 使用测试适配器。不能把测试概括成任意 1 wei 都能阻止任意规模复投。

影响限于复投，不会因此取走 LP 本金或阻止正常买卖。当前池费固定为 0，复投运营尚未启用，因此是**候选功能启用前应修复**的问题，而非已经观测到的线上攻击。

建议将本次费用支出、退款与外来余额分别归账；多出来的余额应隔离，不应令合法复投失败，也不能无条件当作可复投费用。若通过预清理解决，应在同一原子操作内完成并重新验证全部资产边界，单独发送清理交易再重试仍有竞态。

验收：native/ERC20、外来余额大于/小于本次支出、连续复投、授权归零、原始隔离资产不被消费、真实 Permit2 Fork。

### LBR-02｜低，条件性：Locker 缺口会阻止收取足以填补缺口的新费用

位置：`contracts/src/v1/shared/LaunchLockerCompounding.sol:126`、`:179`。

`_collect` 在领取新 LP 费用之前要求已有余额覆盖历史隔离资产与费用账目。若外部资产被扣减，即使 NFT 已累积足够新费用，也无法先收取恢复覆盖。本轮重跑测试：扣掉 1 单位，再积累约 10 单位费用，归集仍失败；外部补回 1 单位后恢复。

这是防止消耗历史隔离本金的严格保护带来的恢复限制。可以保留并提供明确的补足流程；若要允许用新增费用修复，需明确费用承担损失的规则，并在受限收取后核对最终覆盖，不能直接删掉偿付检查。当前无生产扣减证据。

## 奖励设计需要明确的边界

### LBR-03｜高影响、受信任发布者前提：错误 Root 可锁钱或不可逆错付

位置：`contracts/src/v1/modules/HolderRewardsDistributorV1.sol:216`、`:224`、`:294`。

链上校验轮次、区块身份、已到账预算和 Merkle inclusion；**不验证历史余额、分配比例、叶子总额或数据实际可下载性**。已有离线独立复算工具能防止部分操作错误，但发布者可绕过它，不能当作链上保护。

新增测试确认两种不同后果：

- 到账 1 ETH，发布唯一叶子承诺 Alice 2 ETH、轮次预算 1 ETH：Root 被接受，领取因超预算失败。1 ETH 已从 unallocated 划入旧轮次，不能直接给下一轮；同轮 Root 无覆盖、撤销或重分配入口。恢复只能另行补偿等链外安排，原错误轮次资金仍锁定。
- 发布给没有 Meme 的 Bob 后，Guardian 撤销发布者，Bob 仍能按旧 Root 领取。撤销只阻止未来发布，不能止付已发布的错误权益。

这不是未授权用户绕过 Merkle 验证；它是当前已记录的受信任发布和不可修改 Root 设计的具体资金后果。**不建议擅自增加管理员追回合法用户资金的权限。** 在保留设计的前提下，发布前必须完成独立余额复算、叶子金额合计、预算校验、完整数据与 proofs 持久化，并控制发布钱包实际可支配的未分配预算；先落盘再发布。若未来要求链上纠错或挑战期，应作为新经济/治理设计另行决定。

### LBR-04｜中，产品参数未冻结：单点快照不奖励持有时长，费用周期未在链上绑定

位置：`HolderRewardsDistributorV1.sol:42`、`:224`、`:274`；`docs/planning/HOLDER_AUTOMATED_SNAPSHOT_DESIGN_2026-09-13.md:16`。

当前已确认采用钱包单点快照；卖出后保留旧轮次权益是正确实现，不是缺陷。但短期持有人可以获得与同一快照余额的长期持有人相同的当轮份额。若取样区块可预知，可出现快照前买入、快照后卖出的策略；是否有利取决于双向交易成本、滑点及奖励规模，本轮没有证明可稳定获利。区块末余额快照也不能直接称为单笔闪电贷攻击。

新增测试进一步确认：Alice 在区块 1500 已卖出，随后才入金的全部奖励，仍可由发布者按区块 1000 的快照分给 Alice。合约没有 fee cutoff/period 约束；只保证区块递增及预算有资金。该行为可能符合选定政策，也可能是错误混入下一期预算，必须由发布规则区分。

建议先固定取样规则、奖励覆盖期间、费用截止点、重试不重新抽样、迟到资金归属、零合格余额和舍入处理。仅随机延迟发布不等于随机取样。当前 24 小时和随机取样均未冻结，不在本轮替用户选择。

### LBR-05｜已确认设计：不领取可延迟销毁，罚没后可由平台领取

后续确认：用户明确这两项均为预期设计，不属于问题或待修项。保留以下复现作为规则验证，不改变合约行为，也不要求另行确认。

位置：`ProtocolFeeVaultUserClaims.sol:80`、`:207`；`ProtocolFeeVaultLiabilities.sol:144`、`:294`、`:306`；`MemeStockGauge.sol:72`。

普通 Creator/Staker 领取会销毁其 Meme 收益，Quote-only 领取也会结算 Meme；Holder 在归集时销毁，Platform 正常收入不受影响。源码与现有销毁文档在这些方面一致。

需要额外明确两点：

1. Creator/Staker 一直不领取，待领 Meme 不会自动减少 totalSupply。对只有 Meme 收益的地址，领取只付 Gas 而不给本人资产，缺乏主动触发动力。因此不能承诺“发生交易即通缩”或固定期限自动销毁。
2. `rageQuit` 的未领奖励走既有罚没路径。新增测试隔离验证 Gauge 授权的 FeeVault 端点：200 Meme Staker 负债被转入 reserve，平台原本 300 加罚没 200 共领取 500，totalSupply 不变。它没有测试或声称用户能把这笔钱转给自己；真实 Gauge 的调用链已核对。

“罚没归平台”是既有规则，“正常结算销毁”是新开关，两者组合需要明确优先级。若目标仅是领取时销毁，可保留实现并补充例外说明；若目标是所有原归 Creator/Staker/Holder 的 Meme 费最终必烧，则当前实现不足，需要单独批准罚没处理及无人领取时的结算方式。不要借审查修改已接受的本金优先退出。

### LBR-06｜功能交付缺口，已计划 TODO：快照奖励尚未形成自动运营闭环

证据：`tools/holder-rewards/worker.mjs:90` 仍检查旧 `TICKERGARDEN_USER_CLAIM_ASSET_SELECTION_V1`，并调用 `nextStreamStartAt` 等连续奖励接口；当前合约为 raw claim + wallet snapshots。该 worker 不能直接承担新快照发布。

前端适配器已请求 `/v1/holder-snapshots`，但本轮在 Read API 中未找到该路由；已有 analytics 的 holder_snapshots 表是余额统计来源，不能等同奖励轮次、proofs 存储和发布服务。仓库已提供离线 `buildWalletSnapshot`/preflight，但没有据此形成已验收的自动发布链路。

这是已明确延后的工作，不是合约授权漏洞，也不应在本轮擅自启用签名服务。启用 Holder 产品前需完成并验证：手续费归集到账 → 固定轮次预算与样本 → 独立复算 → 证明持久化 → Root 发布 → API → 分资产领取及重启/重组恢复。只部署 Distributor 或只运行旧 worker 不足以完成业务。
